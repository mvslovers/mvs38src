# The IFOX00 oracle

2026-09-06. Every claim about what `as370` *should* do is checked against the
real Assembler XF running under MVS/CE, not against a reading of the manual.
This is how.

## The recipe

```sh
cat > t.jcl <<'JCL'
//IFOXTST1 JOB (ACCT),'MVS38SRC',CLASS=A,MSGCLASS=H,NOTIFY=IBMUSER
//ASM     EXEC ASMFC,PARM.ASM='LIST,NODECK,LOAD'
//ASM.SYSIN DD *
TESTS    CSECT
         ...
         END
/*
JCL

curl -s -u IBMUSER:SYS1 -H "X-CSRF-ZOSMF-HEADER: x" \
     -H "Content-Type: text/plain" -H "X-IBM-Intrdr-Mode: TEXT" \
     --data-binary @t.jcl -X PUT "http://mvsdev:8083/zosmf/restjobs/jobs"

curl -s -u IBMUSER:SYS1 -H "X-CSRF-ZOSMF-HEADER: x" \
     "http://mvsdev:8083/zosmf/restjobs/jobs/IFOXTST1/JOB00001/files"

curl -s -u IBMUSER:SYS1 -H "X-CSRF-ZOSMF-HEADER: x" \
     ".../files/102/records" > ifox.lst
```

`SYSPRINT` of the `ASM` step is usually id `102`; with several steps they run
102, 104, 106.

**Three traps:**

- The **programmer name on the job card is mandatory**. Without it the job dies
  with `IEF633I PROGRAMMER NAME MISSING` before running.
- **Do not set `USER=`/`PASSWORD=`** — mvsMF appends them itself.
- **Do not collect the curl flags in a shell variable.** zsh does not word-split
  an unquoted expansion; you get `command not found` with the whole line as the
  name. See [`../work/README.md`](../work/README.md) — this is the same trap that
  cost a measurement earlier the same day.

## What it has settled so far

| Question | Answer |
|---|---|
| `START 0` | **exactly `CSECT`** — identical ESD entry, `SD 0001 000000 000008` both ways |
| `START 256` | location counter and ESD address become `X'100'`; operand is **decimal**; length measured from the origin |
| `START 5` | ESD address `000008` — **IFOX rounds the origin up to a doubleword** (found by cc370, not by us; our cases 0 and 256 were both already aligned) |
| `ISEQ 73,80` | generates no bytes, does not advance the location counter, flags `IFO025` on a violation **and assembles the offending statement anyway** |
| `DC S(0)` | `0000` — halfword, 4 bits base, 12 bits displacement |
| `DC S(4(3))` | `3004` — explicit base 3, displacement 4 |
| `DC S(sym)` | `C010` — base from the active `USING`, displacement resolved |
| `DS S` | two bytes reserved, no object code, halfword alignment |
| `DC 2S(a,b)` | the duplication factor applies to the **whole operand list**: `0000 C010 0000 C010` |
| `&SYSDATE` / `&SYSTIME` | 8 and 5 characters, `MM/DD/YY` and `HH.MM` — **`as370` matches exactly** |

The `START 5` row is the argument for the oracle in one line. Both sides had
reasoned that the origin becomes the location counter; both were wrong for
unaligned operands, and no case in this corpus would have revealed it.

The `&SYSDATE` row is the argument for the second time. 162 modules in the tree
embed a timestamp, 89 of them in the comparison, and **not one is identical**
against a base rate of 14.7 %. That looked like a cause. One oracle run showed
`as370` expands both exactly as IFOX00 does, and the correlation dissolved into
something else. It also saved building a `--sysdate` option nobody needed.

## What the REST route cannot do

`SYSPUNCH` does not come back byte-exact, not even with
`X-IBM-Data-Type: binary` — it arrives transcoded with non-printables replaced.
So **object-deck comparison cannot go through the spool.** Two routes not yet
measured: FTP in `TYPE I` on ports 2122/2123, or writing the deck to a permanent
data set and fetching it with `dasdcat` while the instance is down.

For everything the assembly *listing* shows — location counter, generated bytes,
ESD, diagnostics — the spool route is enough, and that is most of what the
oracle is asked.

## A class the oracle sized rather than solved

162 modules in the tree contain `DC C'&SYSDATE'` or `&SYSTIME` directly. Far
more reach them through a macro: `MODID` — IBM's module-identification macro,
in `SYS1.AMACLIB` — stamps the assembly date and time into the object, and so do
`JPATCH`, `IQAID`, `BLSDMSGG`, `XCTLTABL` and `SGIEF016`.

Counted over the comparison: **302 modules carry an assembly timestamp, and not
one of them is byte-identical.** At the run's base rate of 14.7 % one would
expect about 44.

The timestamp itself explains only part of that. `as370` expands `&SYSDATE` and
`&SYSTIME` exactly as IFOX00 does — same format, same length — so it cannot
cause the **229** of those 302 that differ in *length*. Two of the stamping
macros, `JPATCH` and `BLSDMSGG`, come from the web mirrors with an unestablished
maintenance level, which puts part of this class straight back into the macro
provenance question.

What is certain: as long as the assembly date differs from IBM's, these 302
cannot compare identical, and the remaining 73 byte-differences include at least
the stamp. Two ways out, neither taken yet:

1. **A `--sysdate`/`--systime` override in `as370`**, set from the date the
   shipped module carries. It makes the comparison possible; it also takes the
   answer from the reference, which weakens the identity claim and should be said
   plainly wherever the number is quoted.
2. **Treat the stamp like a `DS` hole** — name the byte range in a `difin`. More
   honest, and it matches how Dave Kreiss handled the other unavoidable
   differences.

The second is the better fit for this project. Neither is worth building before
the 229 length differences in the class are understood, because a stamp cannot
explain those.
